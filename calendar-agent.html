The problem

A task list says what I need to do, but not how it fits around class, meals, travel, and the energy I have that day. Calendar Agent turns that list into a proposed schedule, then uses completed sessions to make future duration estimates more personal.

The native SwiftUI application follows an earlier Python planner in the same folder. Google Calendar writes follow an explicit Add to calendar action. Optional OpenRouter extraction supplements the local list parser; task entry and deterministic scheduling do not require a model key.

A deterministic scheduling core

TaskParser.swift converts list input into editable task models. Scheduler.swift orders those tasks and searches forward through blocked intervals. Travel and work are placed as one contiguous block, with travel rendered immediately before its task.

An edited or pinned time acts as an earliest task start. If a meeting blocks that time, the scheduler advances to the end of the conflict and tries again. Lunch and dinner are protected intervals. If a whole task plus travel cannot fit before the planning window ends, the scheduler returns a named cannot-fit error.

This is a forward scheduling heuristic, not a global optimization solver. It keeps the selected ordering and does not split a long task across smaller gaps. That makes its decisions traceable, while leaving room for better use of fragmented days.

Estimates with visible evidence

Duration learning uses completed local history. It prefers the same normalized task name, falls back to the task category, and narrows to matching difficulty when available. If similar check-in context exists, it uses those sessions: sleep within 45 minutes, energy within one rating, matching meal timing, and compatible time of day.

Estimates are averages rounded to five minutes. With no relevant history, the parser starts at 30 minutes and reports zero samples. Each estimate carries a sample count, source, and rule-based confidence. High confidence requires at least four same-task sessions with matched context and limited variation; it is a heuristic label, not a calibrated probability.

The efficient ordering alternates harder tasks with easier resets within priority groups; the gentle ordering starts with easier work. Low-energy or short-sleep check-ins can adjust the efficient order, while task priority stays first. These are personal planning rules, not validated health recommendations.

Native interaction and local state

  • Separate the interface from planning rules. SwiftUI views use a planner store, while task parsing and scheduling remain standalone Swift logic that can be checked without launching the app.
  • Remember useful context locally. The planner stores duration history, task names, travel memory, check-ins, and energy logs in an atomically written JSON state file.
  • Capture focus separately from elapsed time. The timer tracks focused time and pause count, supports extensions, and requests a completion entry. This creates richer history than assuming every scheduled minute was spent working.
  • Scope calendar access in the implementation. The Google service uses the signed-in account’s primary calendar. Created events receive an app marker, and event-extension code searches app-managed events before updating them.

What was checked

Fresh standalone Swift checks · November 16, 2026

Seven checks passed against copies of the actual Models.swift, TaskParser.swift, and Scheduler.swift, compiled together in a temporary command-line harness.

  • Explicit durations round to five minutes and remembered travel is restored.
  • A new task exposes a 30-minute estimate with zero historical samples.
  • A busy event shifts the combined travel/task block while preserving adjacency.
  • A task crossing lunch moves after the protected break.
  • A pinned earliest start moves around a conflicting event.
  • An oversized task returns cannotFit.
  • Gentle ordering puts an easier task first within its priority group.

These are focused core-logic checks written for this review, not an existing XCTest suite or an end-to-end app test. Google OAuth, calendar writes, the SwiftUI interface, historical estimation accuracy, and phone integration were not exercised.

Scope and next questions

The folder includes a native macOS app, its Python predecessor, and an iPhone mobility companion. This case study centers on the macOS planning core. Source inspection also found local check-in, energy, focus, and mobility data models; their presence is not evidence of measured productivity gains.

One concrete limit is that the current calendar reader imports timed events through dateTime fields; all-day events are not treated as busy intervals. Live calendar behavior and rescheduling need broader integration checks, especially when extending a running task around other commitments.

The review used implementation files and fresh local checks. Personal calendar data, OAuth files, local history, and API keys are excluded. The portfolio calendar visual remains an illustration.
