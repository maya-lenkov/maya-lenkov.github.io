The problem

An internship application is a chain of small tasks: find a relevant posting, decide whether to apply, tailor the writing, repeat profile information, and track the result. I built a local application desk to keep those steps connected while leaving the applicant in control of the final submission.

Three stages, one application record

01 / FEEDChoose a role

Discovery imports postings; Apply saves an explicit choice and queues preparation.

02 / WAITING TO SUBMITResolve and review

Approve writing, answer missing questions, and open the retained employer tab when its form is verified ready.

03 / APPLIEDTrack the outcome

Record a recognized submission confirmation or an explicit user report, then track the Google Sheets sync.

The current Chrome workflow prepares selected applications in inactive tabs. Sign-in, security checks, agreements, missing facts, and unsupported controls pause the affected application. The user opens the actual employer form for review and clicks Submit themselves.

How the pieces fit together

A Python/FastAPI portal manages documents, preferences, writing, and job history. Source adapters normalize postings from Handshake, LinkedIn, Greenhouse, and Lever. A deterministic relevance filter uses titles and concrete responsibilities; preferred employers and posting dates help order work.

SQLite retains job records and preparation requests. The Chrome extension consumes saved requests, fills supported controls, and reports the tab, session, review state, and configuration revision back to the portal. Resume bytes are cached with a document hash so the extension can refresh its copy when the active document changes.

The folder also contains an earlier Playwright worker and platform-specific adapters, including Workday preparation. Those paths have different review mechanics. Their presence does not establish that every employer layout works in the current extension.

Design decisions that make state trustworthy

  • Save intent before browser work. A persisted Apply request survives a portal restart. The coordinator can recover work after a disconnected content script without treating another click as another application.
  • Make ready a verified state. A selected job needs a verified review page and current settings and response revisions. A stale extension heartbeat removes ready status; an already submitted job cannot re-enter preparation.
  • Bind approval to the writing being uploaded. Responses belong to a job, employer URL, and question. Editing a response revokes its upload approval. A changed profile or resume also invalidates the approved bundle.
  • Ground generated claims. Tailored letters select exact resume/posting evidence IDs and pass a separate model factual audit. Invalid evidence and unsupported claims are rejected, but model audits still need human review.
  • Separate browser preparation from a recorded outcome. Recognized confirmation reports are checked against the retained tab, session, and employer URL. Applied records and the Sheets outbox use the database workflow; opening or filling a form is insufficient.

What the tests establish

Fresh focused run · November 16, 2026

49 tests passed across test_chrome_queue.py, test_tailored_letters.py, test_workflow.py, test_core.py, and test_writing.py. This run used temporary test workspaces and mocked model responses; it submitted no real applications.

  • Queue tests reject unverified or outdated ready states and remove submitted jobs from preparation candidates.
  • Workflow tests check explicit selection, request persistence across restart, stale sessions, and rejection of confirmation reports with the wrong URL, tab, or text.
  • Writing tests verify PDF output, version conflicts, revoked approval after edits, and rejected unsupported generation. Letter tests reject invented evidence IDs.

The repository also contains opt-in synthetic browser tests for popup persistence, bridge reinjection, and multistep preparation stopping at review. Those browser tests were inspected, not rerun for this portfolio update.

Live evidence and remaining work

An earlier local test report records one LinkedIn form reaching final review without a submit click, a generated letter passing a model audit with subsequent local edits, and public Greenhouse/Lever discovery checks. That report also records a Handshake security stop and an unsupported LinkedIn layout. These are recorded checks from an earlier version, not a fresh live verification.

The current evidence supports a working local workflow and focused state-management tests. It does not establish universal ATS support, unattended application submission, or improved hiring outcomes. Production selectors, account access, model quality, and employer-specific controls remain ongoing work.
